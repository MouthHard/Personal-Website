# 适配与兼容规范

> **自迭代提醒**：每次执行前检查业界最新实践（Google / Microsoft / Apple、阿里 / 腾讯、Vue / Vite 官方、web.dev、Web Platform Baseline、MDN、高星 GitHub 项目），对比本文档并迭代，保持规范不过时。任何改动前先询问用户。
>
> **读者**：新会话的 AI 助手或开发者。
>
> **适用范围**：整个项目，不限于 Landscape 子页面。

---

## 1. 目标：只覆盖主流大部分

访客以国内为主，微信内置浏览器必须支持。不追求全浏览器全覆盖，把成本集中在真正会产生问题的地方。

| 档位 | 范围 | 承诺 |
|------|------|------|
| **完整体验**（验收基线） | Chrome / Edge ≥111、安卓微信 X5（近两年版本） | 全功能 |
| **降级可用** | iOS 微信 / Safari 16.4+ | 布局与交互完整；毛玻璃变平、光晕消失可接受 |
| **不承诺** | IE、Opera Mini、Safari ≤14、老安卓 WebView | 零投入 |

**为什么支持微信没有引入新维度**：iOS 微信使用 WKWebView，与 Safari 行为高度一致（微信官方明确「一般情况下无需特别适配」）；安卓微信使用 X5 内核（基于 Chromium，当前基线已到 Chromium 121）。因此「支持微信」= 支持 Safari 16.4+ 与 Chrome/Chromium，都在 Vite 默认覆盖范围内。

## 2. 技术基线（以实际配置为准）

| 项 | 现状 | 含义 |
|----|------|------|
| Vue / Vite / TypeScript / Sass | 3.5 / 7.3 / 5.9 / 1.103 | 现代工具链 |
| **真实编译目标** | Vite 7 默认 `baseline-widely-available` → Chrome 111 / Edge 111 / Firefox 114 / Safari 16.4 | 唯一生效的目标，按 Vite 大版本冻结 |

> **判定原则**：任何兼容问题，先确认是否发生在「完整体验」档内。档外的降级表现不算 bug。

## 3. 响应式适配

### 3.1 断点分层

大厂做法都是少数几个语义档，而不是按设备穷举：Bootstrap 5 用 576 / 768 / 992 / 1200 / 1400，Tailwind 用 640 / 768 / 1024 / 1280 / 1536。本项目据此分两层：

- **全局外壳**：只用 `1280 / 1024 / 768 / 430` 四个主干值，供 Header、页面骨架、SectionNavigator 等跨页面共用。
- **模块内部**：允许内容驱动的断点 `1320 / 1180 / 980 / 900 / 760 / 640`，但必须能说清「哪个内容在这个宽度放不下」。

**纪律**：

- 新增断点必须登记内容依据，禁止无依据的孤立值（480 / 560 / 600 / 720 / 800 这类）。
- 存量散乱断点**只登记、不改存量**；后续改动到哪个模块，顺手把该模块归拢到主干值。
- 同一文件内保持单一写法方向，不新增混用（`max-width:` 与 `width <=` 混用是历史遗留）。

### 3.2 布局原则

- 能弹性就不写死：优先 `flex` / `grid` + `minmax()` + `clamp()`。
- 固定宽度只用于确实需要恒定尺寸的小部件；一旦固定宽度挤压了相邻区域，就必须给窄屏断点让其改为纵向堆叠。
- 装饰元素（伪元素、SVG 光晕）允许伸出视口但不应产生滚动；判定标准以 `documentElement.scrollWidth` 为准，不看单个元素的 bounding rect。

### 3.3 移动安全区

底部固定元素加 `padding-bottom: env(safe-area-inset-bottom, 0)`。`env()` 需要 `viewport-fit=cover` 才生效，按需启用；启用后要确认顶部内容不被刘海遮挡。

## 4. 技术选型准入（稳定优先）

**判定标准只有一个：Web Platform Baseline 状态。** 它把特性分为三阶段，正好对应「较新但不过时」的取值区间：

| 档 | Baseline 状态 | 判定 | 动作 |
|----|--------------|------|------|
| 默认用 | **Widely available** | 四大核心引擎（Chrome / Edge / Firefox / Safari 含 iOS）全部支持满 **30 个月** | 直接用，无需兜底 |
| 观察中 | Newly available | 全引擎已支持，但未满 30 个月 | 不进核心代码，可局部试验并配 `@supports` |
| 不引入 | Limited | 尚未全引擎支持 | 禁用 |

> **为什么选 Widely 这条线**：它恰好是「稳定、安全、较新、不过时」的官方定义——已被整个行业验证至少两年半，又不会老到被淘汰。比逐个特性凭感觉判断可靠得多。查状态用 [web.dev Baseline](https://web.dev/baseline/) 或 Chrome DevTools 元素面板的 Baseline 标记。

**当前项目相关清单**（2026-11 核对，每次迭代时重新查）：

| 档 | 特性 |
|----|------|
| **默认用** | `flex` / `grid` / `gap` / `minmax()` / `clamp()` / `inset` / `:is()` / `:where()` / `color-mix()` / `text-wrap: balance` / `:has()`（2026-06 Widely）/ container queries（2025-08 Widely）/ CSS 嵌套（2026-02 Widely）/ `clip-path` / `AbortController` / `IntersectionObserver` / `matchMedia` / `navigator.clipboard` |
| **观察中** | `field-sizing`（2026-06 Newly）/ 容器样式查询（2026-05 Newly）/ `:open`（2026-05 Newly）/ `image-rendering` / `SharedWorker` |
| **不引入** | `@starting-style` / 滚动驱动动画 / anchor positioning / `oklch()` / `structuredClone` / `findLast()` / `toSorted()`（`oklch` 已达 Widely，但项目 0 使用且现有色彩体系基于 hex/rgb，**没有替换动机就不换**） |

**不要反向操作**：不要用「曾经是新技术」当理由继续给已 Widely 的特性加 `@supports`（本项目早期对 `:has()` / `@container` 就这么做过，属于过 conservative）。规范落后于现实同样会误导。

### 4.1 CSS 三层法（MDN 渐进增强）

适用于「需要用观察档特性」或「需要在降级档保持可读」的场景：

1. 先写全浏览器都能解析的基础声明；
2. 再写现代声明覆盖；
3. 需要能力分支时用 `@supports`。

带前缀的属性写在**标准值之前**，让支持标准值的浏览器覆盖它。

本项目的具体策略：

| 特性 | 策略 |
|------|------|
| `backdrop-filter` | 绝大多数使用处下面已有 `rgba()` 底色兜底，失效只是变平。**不补前缀、不加 autoprefixer** |
| `color-mix()` | 已 Widely，只用于光晕、阴影等装饰，失效也不影响可读性。**不回退** |
| `:has()` / `@container` | 已 Widely，**直接用**，不再强制 `@supports` |
| `oklch()` / `@starting-style` | 不引入；确需使用时必须配 `@supports` 或静态兜底 |
| `mask` / `aspect-ratio` / `inset` | 验收基线全支持，无需处理 |

### 4.2 JavaScript API

- `IntersectionObserver`、`AbortController`、`matchMedia`、`navigator.clipboard` 均已 Widely，**不加 polyfill**。
- 动态能力判断用 `if ('xxx' in window)` 或 `typeof window.xxx === 'function'`，**不要 UA 嗅探**。
- **降级样板**：`src/components/common/PageChange/preload.ts` 对 `requestIdleCallback` 先做 `typeof` 检测再调用，不支持时直接同步执行——新 API 接入都照这个写。
- 不支持的 API 要能静默降级，不能让整页白屏。

### 4.3 微信内置浏览器专项

- 保持 hash 路由，不切换 History 模式（iOS 微信 + JSSDK 授权时 History 会失败）。
- `localStorage` 读写包 `try/catch`：X5 内核配额更严格，非同源 iframe 中会抛 `SecurityError`。
- 不依赖微信 `cache` JSAPI（WKWebView 已不支持）。
- 涉及 JSSDK 时版本 ≥1.2.0。
- 无法区分是 WKWebView 特性还是微信内部逻辑导致异常时，分别在 Safari 和微信里测一次，快速定位。

### 4.4 工具与依赖的稳定性策略

面向「最稳定、最安全」的选型，本项目采用以下组合，**不轻易改**：

- **`^` 版本范围 + 已提交的 `package-lock.json`**：日常安装完全由 lockfile 复现，不会随机漂移；升级走主动 `npm update` 或 `npm install <pkg>@<version>`，不靠重装碰运气。**不要把 `^` 全改成 pin 死版本**，那会让依赖树失去安全修补丁的能力。
- **禁止 canary / next / beta / alpha 标签的依赖**，只装稳定版。
- **新增依赖前先问**：原生 API 能不能替代？项目已用 `knip` 检测未使用的依赖与导出，避免依赖膨胀。
- **安全审计**：`npm audit --audit-level=high` 纳入验证；发现漏洞时手工评估，**不用 `npm audit fix --force`**（会跨 major 版本，破坏 API）。
- **升级节奏**：主线版本发布后观察 1–2 个 minor 再跟进，不追首发。

### 4.5 HTML 与图片

- `<img>` 统一带 `loading="lazy"`（首屏关键图除外）与 `decoding="async"`。当前 158 个 `<img>` 中 lazy 覆盖较好，`decoding` 仅 1 处，属可批量补齐的低风险项。
- 图片给显式 `width` / `height` 或 `aspect-ratio`，避免加载时布局跳动（CLS）。
- **禁用 `user-scalable=no`**：MDN 明确 iOS 10 起直接忽略该声明，且会损害无障碍。
- `viewport-fit=cover` 与 `env(safe-area-inset-*)` 按需启用，见 3.3。

## 5. 落地优先级与不做清单

**只做两件事**：

1. **P0** — 修全局 Header 响应式。这是唯一实测会破版的问题：约 1290px 固有宽度导致 900px 起导航项被裁、768px 只剩 4 个、360px 只剩 1 个，且影响全部 8 个 Landscape 子页面。一处修好，全站受益。
2. **P1** — 借真机在微信里各验一次 iOS 与安卓。

**不做**（投入产出比低，或当前档位不需要）：

- `@vitejs/plugin-legacy`
- 下调 `build.cssTarget`
- 添加 autoprefixer
- Safari 全版本矩阵实测
- 断点全量收敛重构
- 改 `browserslist`（当前不生效）

## 6. 验证清单

1. **Chromium 四档宽度**：1440 / 1024 / 768 / 390。判定：
   - `document.documentElement.scrollWidth === clientWidth`
   - Header 导航项完整可见
   - 无 console error
2. **微信真机各一次**：iPhone 看毛玻璃/光晕降级是否可接受，安卓看布局与点击是否正常。
3. **静态检查**：`npm run typecheck`、`npm run lint:check`、`npm run lint:css:check` 全绿。
4. **依赖安全**：`npm audit --audit-level=high` 通过；`npm ci` 能复现依赖树。
5. **测量纪律**：溢出检测必须等动画稳定（≥1.5s）后连测 3 次取最大值。动画未结束时扫描会产生大量假阳性，同一组合两轮结果会完全不同。
