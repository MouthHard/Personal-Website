# Bug 记录体系

> **⚠️ 每次执行之前都要检查 GitHub 项目和大厂规范的 bug 及其解决方案，并依次来迭代本文档和记录规范。**
>
> **用途**：记录每次出现的 bug、根因分析、解决方案、思考过程，避免同类问题重复出现。
> **读者**：新会话的 AI 助手或开发者，通过这些记录理解"这个问题之前怎么解决的"。

---

## 为什么要记录 Bug

代码修复只记录了"改了什么"，但不记录"根因是什么"、"考虑了哪些方案"、"为什么选这个方案"。
当类似问题再次出现时，如果没有这些记录，容易：
- 重复同样的排查路径，浪费时间
- 忘记之前的根因，治标不治本
- 在相似场景下犯同样的错误

## 记录什么

每个 bug 记录以下内容：

| 维度 | 说明 |
|------|------|
| **症状** | 用户看到了什么？什么场景下触发的？ |
| **根因** | 问题的本质原因是什么？（不是表面现象） |
| **排查过程** | 从症状到根因，经过了哪些步骤？ |
| **方案对比** | 考虑了哪些修复方案？各自优缺点？ |
| **最终方案** | 选了哪个？为什么？ |
| **验证** | 怎么确认修复有效？ |
| **预防** | 以后怎么避免同类问题？ |

## 怎么记录

1. **目录结构**：按 bug 类型/模块组织
2. **文件命名**：`日期-简短描述.md`，如 `2026-10-30-SCSS嵌套导致弹窗不可见.md`
3. **时机**：bug 修复后立即记录，不要事后补
4. **粒度**：一个记录文件对应一个独立的 bug

## 目录结构

```
docs/bugs/
├── README.md              # 本文件
├── css/                   # 样式相关 bug
├── path/                  # 路径/构建相关 bug
├── performance/           # 性能相关 bug
├── git/                   # Git/部署相关 bug
└── logic/                 # 业务逻辑相关 bug
```
